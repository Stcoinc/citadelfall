## Current Product Direction

- Build a Unity Asset Store-style tower defense engine/tool.
- Also build a real playable MVP game with it.
- Citadel Fall Arena is the primary game: five-hero deck, random mana summons, a 3 x 5 board, same-rank merging, short deterministic matches, and future equivalent-board versus play.
- Adventure Defense is the secondary offline campaign and creator-engine mode: direct hero selection, authored paths/sockets, Scrap placement, upgrades, selling, and longer missions.
- The three modes are intentional. Arena is the primary merge-defense game; Adventure is the finite campaign; Endless is direct-placement score attack. They share the application shell, account, progression, content catalog, heroes, enemies, prefabs, and combat services while retaining mode-specific rules and HUDs.
- Primary creator audience: non-developers.
- First workflow target: create one playable TD level in about 10 minutes.
- Content should be JSON-driven so new levels and balance can later come from storage or a database without app updates.
- Current playable-game theme: fantasy adventure tower defense, not fleet or spaceship combat.
- Player towers are fantasy defenders. Initial roster: Mage, Warrior, Paladin, Archer, Druid, and Sorcerer.
- Initial enemies: Rat, Wolf, quick Goblin, and strong Orc.
- Protect fantasy strongholds in either the Arena pressure lane or Adventure's authored paths and sockets.
- Existing sci-fi names, IDs, prefabs, and art are transitional and should be migrated incrementally without breaking reusable engine schemas.
- Target platforms are mobile, PC, and WebGL.
- Firebase integration should use REST APIs so it works across mobile, PC, and WebGL.
- REST foundation: `IRestClient` lives in Application; `UnityRestClient` lives in Infrastructure and wraps `UnityWebRequest`.
- Multiplayer is required, but the early architecture should use deterministic seeds and low-frequency commands instead of high-frequency state sync.
- Placeholder assets are acceptable; replaceable assets and generated placeholders are useful.

## Owner Preferences

- SOLID architecture.
- One primary class per file.
- No classes over classes in the same file.
- Private fields use `_privateVariable` / `_camelCase`.
- Public variables or properties use `PublicVariables` / PascalCase only when actually needed.
- Build reusable systems rather than one-off game-specific scripts.
- Do not make non-developers touch code for normal content creation.
- Use Unity's new Input System, not the old input manager.

## Current Foundation Status

- Unity version: `6000.3.7f1`. The folder is not currently a Git repository.
- Enabled build scenes include `Intro.unity`, `MainMenu.unity`, `LevelSelection.unity`, `Gameplay.unity`, `CitadelFallArena.unity`, and `Endless.unity`. `MvpGameplay.unity` and `FullGame.unity` are historical preserved scenes and remain disabled.
- Application flow: Intro loads validated remote/local content and restores authentication; Main Menu owns entry/profile/auth/collection; Level Selection owns save profiles, campaign maps, shop, and the Arena profile gate; gameplay then loads Adventure Defense or Citadel Fall Arena.
- `AppRuntimeSession` holds the active immutable catalog, selected save slot, selected level, and routing state. `AppServicesBootstrap` is scene-authored and persistent.
- Current authored/runtime content: 15 tower/hero definitions, 7 enemies, 5 wave sets, 10 levels, 1 battlefield template, and `arena_standard` rules.
- The six active fantasy heroes are Mage, Warrior, Paladin, Archer, Druid, and Sorcerer. Generic `Tower` terminology remains internal compatibility language.
- Arena has fifteen authored sockets, five-hero deck selection, deterministic summon/socket/enemy streams, mana and rising summon costs, same-hero/same-rank merges, rank scaling, stronghold lives, waves, bosses, timer, tutorial, results, replay/menu actions, and persistent rewards/statistics.
- Adventure Defense uses six scene-authored sockets, direct hero selection, Scrap placement, upgrades, configured merges, selling with a default 40% refund, authored waves/path, victory rewards, and the first-free Warrior emergency rule while the board is empty.
- Enemy content is Rat, Wolf, Goblin, Orc, Orc Bulwark, Runestone Troll, and Thorn Warden. The six Arena families use exact 8 x 5 directional/death sheets with 240 named frames on the shared enemy prefab.
- `TargetingSelector` is pure Application logic. `EnemyRegistry` adapts live `EnemyAgent` objects, and path progress is distance-based. Damage affinities, projectiles, impacts, splash, upgrades, and merges are data-driven/testable services.
- Account features include registration, username/email login, eight required avatar choices, email-verification request, encrypted refresh-token persistence, Intro session restoration, username/avatar/level profile display, and logout.
- Player progression stores XP/level, durable Scrap and Coins, unlocked tower/hero IDs, Arena deck, enemy defeat/card progress, campaign/save data, and Arena match records. Valid currency changes persist immediately locally and queue authenticated Firebase progression saves.
- Enemy Chronicles currently presents Rat, Wolf, Goblin, and Orc card progress; each 1,000 defeats advances the collectible tier.
- Text presentation uses TextMeshPro with `MedievalSharp-Regular SDF`. No project-script references to legacy `UnityEngine.UI.Text` remain.
- Unity scenes own paths, sockets, cameras, and UI. ScriptableObjects author local content; the validated `starter_content.json` catalog is the offline fallback and Firebase-compatible contract. Remote values never mutate an active match snapshot.
- Firebase development paths remain `/gameSettings/development/activeVersion` and `/gameSettings/development/versions/{activeVersion}/starterContent`. Production security rules, emulator denial tests, and a live networking provider are not complete.
- New Input System pointer/touch and `InputSystemUIInputModule` remain required. Do not reintroduce `OnMouseDown` or the old Input Manager.
- Scene/prefab UI remains authored. Editor tools may modify approved authored hierarchies but runtime code must not build production UI trees.
